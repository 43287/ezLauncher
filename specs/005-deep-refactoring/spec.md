## User Scenarios & Testing *(mandatory)*

### User Story 1 - 修复底层系统热键死锁隐患 (Priority: P1)

作为一名依赖快捷键呼出应用的用户，我希望在极端情况（如触发 UAC 权限弹窗、系统锁屏、焦点丢失）后，应用内部的快捷键状态机依然能保持正确，不会出现快捷键彻底失效卡死必须重启应用的尴尬情况。

**Why this priority**: 快捷键是启动器应用的核心交互方式，若发生永久性失效，将直接导致软件不可用，这是最高优先级的稳定性问题。

**Independent Test**: 
1. 按下系统全局修饰键（如 `Alt` 或 `Ctrl`）。
2. 在释放之前，模拟系统拦截或焦点丢失（如强制锁屏再解锁）。
3. 再次尝试呼出启动器的快捷键组合，应用能正常响应，说明状态机未被死锁。

**Acceptance Scenarios**:

1. **Given** 应用程序在后台运行并注册了组合快捷键，**When** 用户按下修饰键但触发了系统级弹窗导致释放事件丢失，**Then** 下一次完整的快捷键输入依然能成功唤醒应用，内部状态机能够自动重置。

---

### User Story 2 - 优化数据读写性能与 I/O 效率 (Priority: P2)

作为一名长期使用该启动器的用户，我希望当我的应用列表中有几百个应用时，无论我是修改某一个应用的图标，还是重新排序，系统都不会因为全量的文件读写和加解密而产生哪怕一毫秒的界面卡顿，保证极致的流畅。

**Why this priority**: 全量写回在数据量增长后会成为明显的性能瓶颈，不仅拖慢操作反馈，还加剧了磁盘磨损和 CPU 负担。

**Independent Test**: 在应用中导入 200+ 个快捷方式。尝试快速连续修改多个分类的名字或拖拽排序，界面的操作响应时间依然应当与空列表时一样顺滑。

**Acceptance Scenarios**:

1. **Given** 拥有大量本地持久化数据的状态下，**When** 用户执行高频的轻量级状态修改（如拖拽排序），**Then** 系统的数据同步策略不会阻塞前端主线程，界面不会发生帧率掉帧（FPS 稳定）。

---

### User Story 3 - 重构前后端通信桥梁 (Priority: P3)

作为系统维护者，我需要一个高内聚低耦合的架构，确保各种后端能力（系统执行、配置存储、热键注册等）不再堆积在一个“上帝对象”中，并且前后端的数据模型类型（Type/Struct）能够保证绝对的安全与同步。

**Why this priority**: 这是为了项目的长期演进和可维护性铺路，避免牵一发而动全身。

**Independent Test**: 开发人员能够轻易地在独立的模块文件中找到对应领域（Domain）的 API，并在前端获得完整的类型提示（无需手动维护多份相同定义的 Schema）。

**Acceptance Scenarios**:

1. **Given** 现有的前后端通信层，**When** 进行解耦重构后，**Then** 原有的所有功能（如启动应用、读取设置）正常运作，且代码文件按领域被合理拆分。

---

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 具备键盘钩子（Hook）状态机的超时强制清理能力，即设定超时探针，若修饰键被记录按下超过特定时间阈值则强制复位，以应对系统级中断导致的事件丢失。
- **FR-002**: 系统 MUST 优化持久化写入策略，采用后台线程卸载（异步）方案，将序列化和 AES 加密等耗时 I/O 任务交由 Tauri 的专用后台线程执行，彻底解放前端主渲染线程。
- **FR-003**: 系统 MUST 重新划分后端 IPC 层的职责边界，将原先单一的 API 集合拆分为多个按领域划分的独立模块。
- **FR-004**: 系统 MUST 保证前端状态管理（Store）职责的单一性，将其中的后端通信（副作用 API）剥离到单独的中间层或服务层中。
- **FR-005**: 系统 MUST 明确并统一前后端共享的数据结构契约，使用 `ts-rs` 库在编译时由 Rust 结构体自动生成 TypeScript 的 interface，消除隐式属性或冗余类型的错误逃逸。

### Key Entities

- **ShortcutConfig (Backend) / LaunchItem (Frontend)**: 应用与快捷键配置实体，需保证前后端字段定义的绝对对齐。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 异常丢失焦点测试下，快捷键恢复率达到 100%（不再出现需重启软件才能恢复的死锁现象）。
- **SC-002**: 在 500 个快捷方式的大流量压测场景下，连续执行 10 次拖拽操作，界面渲染帧率（FPS）全程维持在 60 帧以上，主线程卡顿（Long Task）发生次数为 0。
- **SC-003**: 代码架构评估中，IPC 入口文件（如原 `commands.rs`）的代码行数或职责复杂度大幅下降，拆分为至少 3 个以上的独立领域模块。

## Assumptions

- 假设用户在使用过程中可能遇到高频率的系统弹窗（UAC）或锁屏行为。
- 假设未来的应用数量可能会增长到让当前全量序列化成为明显瓶颈的程度。
- 假设前后端的数据契约目前依靠人工对齐，具有易错风险。
